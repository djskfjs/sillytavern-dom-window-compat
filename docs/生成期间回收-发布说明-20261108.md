# 0.4.3-compat.6 发布说明：生成期间暂停前端回收

日期：2026-11-08。基于本地 `0.4.3-compat.5` 兼容实现的修复统一发布为 `0.4.3-compat.6`，继续使用原 GitHub 仓库。发布前核对 GitHub 默认分支仍为 `0.4.3-compat.4`；本次同时包含后台暂停、异常保留页面、不自动刷新以及生成期间暂停前端回收的保护。

## 复现到的问题

用户报告聊天生成中或生成刚结束时，酒馆页面白屏、重新加载；朋友的 Via 浏览器也出现。

核对酒馆助手 4.12.0 / `40e4b72` 的 `src/store/iframe_runtimes/message.ts`：处理 `TH_REQUEST_RENDER_MESSAGE` 时，除了移除目标楼层的 runtime，还会审计其他已挂载楼层；这一路没有检查当前是否正在生成。关闭助手的流式渲染并不会阻止这条审计路径为生成中的代码块创建前端。

使用合成聊天、流式新增楼层、原生滚动及助手生命周期模型进行旧版对照：

| 场景 | 旧版生成期间的补渲染调用 | 旧版生成期间的回收信号 | 未完成回复中的前端 |
| --- | ---: | ---: | ---: |
| 停留底部，新增流式回复 | 0 | 0 | 0 |
| 新增流式回复期间翻历史 | 1 | 5 | 1 |

这证明扩展能在生成期间额外触发前端工作。它会与酒馆继续替换回复正文的过程重叠，但不能仅凭此证明用户手机白屏的直接原因，也没有在电脑中复现真实的内存不足或页面进程崩溃。

## 修改

生成期间保留已有窗口，暂停窗口移动、补渲染和新的逐层回收。回复继续由酒馆输出。生成结束或停止后，等待原生生成标记清除及收尾事件，再恢复用户设定的窗口范围。紧接着开始下一轮生成时继续等待。

已经开始的一个助手调用不能强行中止；该调用后续的回收和补渲染不会继续叠加。原生助手、其他扩展自行发起的渲染、聊天数组、图片、全局脚本和单个复杂前端的内存用量，不受这项修复完整控制。

代价是生成期间暂时不能补载当前窗口以外的历史楼层；现有内容保持显示，结束后恢复。新增回复在生成期间可能让已加载楼层暂时超出窗口层数，结束后会回收。没有修改窗口层数或聊天保存内容。

## 验证方式

新增 `tests/generation-safety.mjs`，覆盖普通流式回复、生成时翻历史、运行中的恢复与回收被生成打断、停止事件先于原生收尾、后台结束、连续生成、生成中开启，以及连续 30 轮生成。检查没有新增的生成期助手调用、聊天数据未被修改、末楼元素保留、结束后楼层数收敛、无脱离页面的助手 runtime。

测试采用桌面 Chrome 和桌面 WebKit 的合成模型；它们不能替代真实 Via/iPhone、具体角色卡和其他已安装扩展的验证。完整结果和命令记录见本包的 `生成期间回收-测试结果-20261108.json`。

## 更新和复测

推荐在酒馆「管理扩展程序」中更新原来的 DOM Window 兼容测试版，然后刷新酒馆页面，确认版本为 `0.4.3-compat.6`。无需安装另一份扩展或重启服务器。手动 ZIP 安装按以下步骤操作。

1. 等当前回复结束，备份原扩展目录。
2. 用安装包中的 `sillytavern_dom_window` 文件覆盖实际 DOM Window 扩展目录；若原目录名称不同，将文件复制到原目录内。只保留一份启用的 DOM Window。
3. 手动刷新酒馆。版本应显示 `0.4.3-compat.6`；生成时应显示“生成中，暂缓回收”。“复制诊断信息”中的 build 为“生成期间暂停前端回收”。
4. 使用原来会出问题的聊天和原窗口层数，比较生成、生成时翻历史、连续生成的表现。

如果再次白屏，等酒馆页面重新加载完成后，立即到 DOM Window 设置中点击“复制诊断信息”，保留完整文本；无需再手动重启服务器。浏览器保留会话存储时，信息包含上次页面的部分状态及是否记录到扩展主动刷新，不包含聊天正文或密钥。关闭标签页、再次刷新或浏览器清掉会话数据可能影响记录保留。没有主动刷新标记，仍不能单独认定是内存不足。

回退时用备份覆盖相同目录并刷新，不需要删除聊天或角色数据。
