# 酒馆助手前端回收适配

本版核对对象是 `n0vi028/JS-Slash-Runner` 的 4.12.0，源码提交 `40e4b72`。源码只用于本地审查，未把整个助手打包进本扩展。

## 确认的问题

`src/store/iframe_runtimes/message.ts` 的 `calcToRender()` 从当前 DOM 首层到聊天末层计算渲染范围。`auditRuntimes()` 按楼层编号保留 runtime，没有验证旧 `elements` 是否仍连接到页面。

阅读窗口向上移动并回收后方楼层时，旧楼层编号仍在这个数字范围内。直接删除 `.mes` 不会从助手的 runtime 列表移除它；Vue Teleport 的旧目标、组件 resize 监听及 Blob URL 等可能继续被保留。源码能够说明这条保留路径，但不能单独证明某次 iOS 页面重载的直接原因。

`src/panel/render/Iframe.vue` 会在 Vue 组件卸载时取消相关作用域监听、撤销 Blob URL。消息内脚本在实际 pagehide 时也有事件清理，因此不应把助手概括成“完全不清理”。

## 本版做法

1. 保留阅读窗口中重叠的 DOM，不把已有 iframe 在父节点内再次移动。
2. 回收楼层时立即移除本扩展的待恢复引用，再移除 DOM。
3. 确认目标楼层已不在当前 `#chat` 直属节点中后，向已核对的助手发送内部 `TH_REQUEST_RENDER_MESSAGE` 信号。
4. 4.12.0 handler 会移除该目标的旧 runtime；因为当前 DOM 不存在，不会重建该楼前端。它仍可能审计并渲染其他已挂载楼层，因此先完成回收，再补挂新范围。
5. 助手的 DOM 替换监听可能自动恢复前端，队列看到对应 TH iframe 已存在时复用它，避免重复刷新。

本扩展不发送 `MESSAGE_DELETED`，不修改聊天数组，也不接管助手脚本 iframe。没有使用 Pinia 私有状态写入。

这个信号不是文档保证的公开卸载 API，所以严格检查助手版本、事件接口与普通渲染条件。目前只有 4.12.0、深度 0、非流式模式通过核对；条件不符时拒绝开启，而不是继续使用未经验证的清理机制。

## 验证边界

模拟回归覆盖数字范围保留、强引用、缺 DOM 时审计、同 mesid 的 DOM 替换监听、窗口复用和 120 轮往返。模拟每层一个 iframe，所以“最多 11 层 runtime”不是“真实页面最多 11 个 iframe”，也不是内存 MB 上限。

iOS Safari、真实前端的网络请求/动画/脚本和浏览器资源回收仍需要真机验证。若重载更频繁，应暂停使用扩展。
